# 工坊缓存与加载流程

实施日期：2026-11-01。适用于当前桌面程序和 CLI 的工坊浏览资料；缓存目录与设置、配置清单、游戏文件分开。

## 页面如何读取

- 搜索只请求当前 Steam 页，不预取后续页或整个工坊目录。未打开条目的摘要仅随查询页保存，不再为整页重复生成独立条目文件。
- 搜索页优先读取内存与磁盘快照。新鲜页面直接使用；一天以内的旧页面先显示并更新，更新失败保留旧内容和失败提示。
- 从导航打开创意工坊页面时更新当前在线列表；可以先展示已有缓存，再完成本次来源更新，停留期间没有定时请求。
- 从列表打开详情，立即显示所选发布的标题、简介、封面与本页已知发布选择，再按需补全介绍。完整且新鲜的详情不因返回、重开或切换页面而重复请求。
- 列表摘要和作者完整介绍明确区分。界面在补全前显示“简介”，不能仅因描述字段非空就认为已读取完整资料。
- 刷新按钮主动重新查询资料；通常浏览仍按缓存时效复用。工坊刷新与全局本地加载状态分开，等待后台资料时仍可更换搜索、翻页或返回。
- 较旧修订、较旧列表和迟到请求不能覆盖更新资料或新页面。失败回退也会重新比较当前缓存，避免恢复请求开始时的旧副本。
- 当前资料须为完整、新鲜且适配声明匹配，才启用应用内下载入口。旧资料可以浏览，刷新失败不会将旧资料重新标成已核验。

## 缓存对象与时效

| 内容 | 键与范围 | 规则 |
| --- | --- | --- |
| 查询页 | 来源、游戏 App ID、语言、热门周期、搜索词、排序、全部标签与页码 | 两分钟新鲜，一天以内可先显示再更新；保存完整来源页，按当前目标版本重新投影。 |
| 已打开的条目资料 | 游戏 App ID 与 PublishedFileId | 两分钟新鲜、最长一天；打开详情时读取，失效或缺失时向 Steam 查询。 |
| 图片字节 | 完整图片 URL 的 SHA-256 | 来源缓存指令优先，本地默认／上限七天新鲜；允许展示的旧图最多三十天，更新后替换当前控件的解码图片。 |

来源更新时间与采集时间分开：读缓存、重新序列化、列表再次看到同一修订，都不延长完整详情的采集时间。同修订优先保留完整介绍；更晚修订的摘要会使旧正文需要补查，而非拼成一份未经来源返回的“完整资料”。

项目中的 `Releases` 仍是已加载条目的聚合，不是 Steam 完整历史文件库。目标游戏版本变化时重新筛选；若来源查询本身带不再适用的版本标签，则需要重新搜索。

## 磁盘目录和恢复

程序通过 `Environment.SpecialFolder.LocalApplicationData` 定位应用数据目录。CK3 保持原 `Ck3ModManager` 根目录；其他游戏使用其 `games/<游戏ID>` 子目录。资料文件及 envelope 也校验游戏 App ID，封面按公共 URL 共享字节缓存。

```text
<游戏数据目录>/cache/v1/
├── pages/       # 查询页 JSON
└── items/       # 条目资料 JSON

<应用数据根目录>/cache/v1/previews/
├── <url哈希>.json                 # 图片索引、采集时间与 HTTP 验证器
└── <url哈希>.<内容哈希>.bin        # 图片字节
```

每个游戏的资料 L1 最多 4 页和 32 条目；磁盘最多 16 页、64 条目，资料文件合计上限 4 MiB，每个 JSON 最多 4 MiB。全应用共享的图片缓存内存最多 8 MiB、磁盘最多 32 MiB，每张最多 5 MiB，索引最多 64 KiB。资料缓存与图片内存按使用顺序淘汰；图片磁盘按索引最近写入／读盘时间淘汰，图片内存命中不更新磁盘顺序。使用时间不作为新鲜度判断依据。

首次读取和列表写入检查磁盘容量和遗留临时文件，超限时按使用顺序淘汰。列表使用页摘要和已在内存核对过的兼容声明。打开详情时单独校验本地正文有效期和修订，写入详情或显式维护时清扫过期文件。

桌面通过只读流解码封面，列表和详情各自管理位图。需要修改图片字节的调用方仍可取得独立数组。

文件使用独立临时文件和原子替换，写入时使用同目录短锁。文件损坏、格式不兼容、游戏／键不匹配或超限按未命中处理；磁盘不可写时仍能使用已取得的网络资料与有界内存缓存。缓存不会覆盖设置或用户配置清单。

## 图片与 HTTP

图片继续验证 Steam 来源、HTTPS、重定向、响应类型和大小。记录 ETag／Last-Modified，在适用时条件请求并复用 304 的本地正文。`no-store` 不缓存，`no-cache` 和过期后的 `must-revalidate` 不跳过验证；这些要求优先于本地默认期限。列表与详情并未因此获得通用 HTTP 响应磁盘缓存，它们持久化的是解析后的业务对象。

各行和详情页独立解码并管理 Bitmap，缓存只共享字节，避免一处释放图片影响另一处。同一在途请求可以共享，取消一个调用方只撤销自己的等待，最后一个等待者离开才取消底层请求。
