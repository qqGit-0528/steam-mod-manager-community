# ADR-0001：采用本地分层的工坊业务缓存

日期：2026-10-28。状态：**Proposed（本轮推荐方案，未实施）**。

## 背景

当前 CK3 工坊列表已有两分钟内存缓存，重启后重新联网；首屏诊断显示等待主要发生在 Steam 读取。PCL 提供对象内存复用、带版本的 JSON 持久化及图片文件缓存等参考，但 Steam 元数据、适配声明和目录型 Mod 的身份需要独立处理。

依据：[已核验的缓存共性](../cache-common-model.md)、[性能与响应头采样](../workshop-performance.md)。

## 决定

建议采用 [CK3 缓存架构方案](../cache-architecture.md)：

- Application 编排新鲜／过期／缺失状态，向界面提供缓存快照和后续刷新通知。
- Core 定义对象身份、缓存端口及元数据合并规则；目标适配筛选首版实时计算。
- Infrastructure 实现有界 L1 内存、L2 JSON 页面／条目缓存与独立图片字节缓存。
- 保留现有 Steam 来源接口，HTTP 协商按实际响应启用；实际 Mod 文件下载继续交由 Steam。
- 分层共用：列表与资料补查共用传输基础；列表向详情直接传聚合项目及所选发布，已有资料无需二次请求；发布列表与本地资料各自管理缓存。完整描述、资料更新及实时核验按需请求。
- 普通刷新失效会话对象，保留 HTTP 磁盘响应缓存；来源重新验证、业务旧快照保留和显式全量清理是不同操作。
- 列表／详情先采用两分钟新鲜、最多一天旧资料展示；图片遵守来源约束，无指令时采用 PCL 七天的初始应用策略。所有值可调整。

首版使用本地文件，不引入 Redis 或数据库；避免为单机桌面缓存增加单独服务依赖。来源与存储端口可分别替换。

## 方案比较

| 备选 | 本轮判断 |
| --- | --- |
| 仅给 HttpClient 加磁盘缓存 | 不能完整表达过期资料先展示、环境重筛或最新详情优先，且列表本轮缺少可用协商头；不作为主体。 |
| 仅在视图模型落盘 | 混合界面状态与持久化规则，CLI 无法复用；不采用。 |
| 本地对象缓存＋应用层编排 | 覆盖当前首屏、重启复用和一致性需求；本轮推荐。 |
| Redis／服务端统一目录 | 需要额外进程或远端服务，超出当前桌面缓存目标；当前不采用。 |
| SQLite 存储 | 未来对象量或事务要求增加时可替换文件存储；本轮暂不引入。 |

## 后果

能在保持 Steam 读取路径的同时增加跨启动复用，并将来源资料、用户选择和适配判断分开维护。新增成本是二阶段界面更新、缓存格式与清理、共享请求生命周期以及摘要／详情一致性规则。普通对象刷新仍可复用符合规则的 HTTP 响应缓存；首次完全缺失、来源重新验证和实际文件下载仍依赖网络。

## 实施约束

按架构方案 A～D 阶段推进；A 阶段同时完成页面缓存、详情合并和界面通知。新服务接管后移除原页面缓存的重复职责；以临时目录、可控时钟和来源替身验证，不能只用一次真实网络耗时验收。
